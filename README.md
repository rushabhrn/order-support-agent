# Order Support Agent

A small but real LLM tool-calling agent: a FastAPI service that answers customer
questions about orders by deciding, on its own, when to look up real data in
MongoDB or calculate a refund — using Groq's OpenAI-compatible function-calling
API. No agent framework (no LangChain) — the tool-calling loop is hand-written
so the whole mechanism is visible and explainable end to end.

## Tech stack

| Layer              | Choice                                                                                  |
|--------------------|-----------------------------------------------------------------------------------------|
| API                | FastAPI + Uvicorn                                                                       |
| LLM / tool calling | Groq (`llama-3.3-70b-versatile` by default, configurable via `GROQ_MODEL`), OpenAI-compatible function-calling API |
| Database           | MongoDB 7 (order records + per-session conversation history)                            |
| Containerization   | Docker + Docker Compose (app + MongoDB, persistent volume)                              |
| HTTP client        | `requests` (no SDK — raw API calls)                                                     |

## Architecture

```
 User message
      │
      ▼
 FastAPI  /chat  ──────────────►  MongoDB (conversations)
      │                              ▲ save turn
      ▼                              │
 agent.run_agent()                   │
      │                              │
      ├─► Groq chat/completions  ◄───┘ (prior history + tool schemas)
      │        │
      │        ▼
      │   tool_calls? ──No──► return plain-text reply
      │        │
      │       Yes
      │        ▼
      │   run matching Python tool  ──►  MongoDB (orders)
      │        │
      │        ▼
      │   feed tool result back to Groq, loop (max 5 steps)
      ▼
   final reply
```

## How it works

1. **`tools.py`** defines two tools as plain Python functions, plus a JSON-schema
   description of each — the format every major LLM provider's function-calling
   API expects — and a registry mapping tool names to functions:
   - `get_order_status(order_id)` — looks up a real order in MongoDB.
   - `calculate_refund(amount, refund_percentage)` — computes a refund.
2. **`agent.py`** sends the conversation + tool schemas to the model. If the
   model responds with a `tool_calls` request instead of plain text, the code
   runs the matching Python function, feeds the result back as a `tool`
   message (linked by `tool_call_id`), and asks the model again — looping until
   it returns a plain text answer.
3. **`db.py` / `main.py`** wire this into a FastAPI `/chat` endpoint. MongoDB
   stores both the order data the tools query and the conversation history per
   `session_id`, so follow-up questions ("how much would a refund be?") have
   context from the turn before. Sample orders are seeded on startup.

## Example interaction

Replies are generated by the model, so exact wording varies between runs.

```
You: What's the status of order ORD1001?
→ agent calls get_order_status(order_id="ORD1001")
→ MongoDB returns: {item: "Wireless Headphones", status: "shipped", amount: 2499.0, ...}
Agent: Your order ORD1001 (Wireless Headphones) has shipped and should arrive
       in about 2 days.

You: If I cancel it, how much would a 50% refund be?
→ agent calls calculate_refund(amount=2499.0, refund_percentage=50)
Agent: A 50% refund on your ₹2,499 order would come to ₹1,249.50.
```

Both tool calls are real — the model decided to invoke them, and the numbers
come from actual MongoDB data and actual arithmetic, not scripted text.

## Guardrails and failure handling

- **Loop cap:** the agent stops after `MAX_STEPS = 5` model calls and returns a
  fallback message instead of looping forever.
- **Unknown tools:** if the model calls a tool that doesn't exist, it receives a
  structured `{"error": ...}` result instead of the request crashing.
- **Missing data:** `get_order_status` returns an error for unknown order IDs,
  so the model explains the problem instead of inventing a status.
- **Grounded answers:** the system prompt forbids guessing an order's status,
  and temperature is set to 0.2 for consistent answers.

## Run it locally

1. Get a free Groq API key: https://console.groq.com/keys
2. Clone the repo and move into the app folder:
   ```
   git clone https://github.com/rushabhrn/order-support-agent.git
   cd order-support-agent/agent-demo
   ```
3. **With Docker** — Docker Compose reads `GROQ_API_KEY` (and optionally
   `GROQ_MODEL`) from your shell environment:
   ```
   export GROQ_API_KEY=your_key_here
   docker compose up --build
   ```
   On Windows PowerShell, use `$env:GROQ_API_KEY="your_key_here"` instead of
   `export`.
4. **Without Docker** (needs a local MongoDB running on port 27017):
   ```
   pip install -r requirements.txt
   export GROQ_API_KEY=your_key_here
   uvicorn main:app --reload
   ```
5. In another terminal, run the end-to-end script:
   ```
   python test_agent.py
   ```
   You should see the agent look up ORD1001's real status, then calculate a
   refund using that order's actual amount.

### Configuration

| Variable       | Required | Default                     | Purpose                     |
|----------------|----------|-----------------------------|-----------------------------|
| `GROQ_API_KEY` | Yes      | —                           | Groq API key                |
| `GROQ_MODEL`   | No       | `llama-3.3-70b-versatile`   | Groq model used by the agent |
| `MONGO_URI`    | No       | `mongodb://localhost:27017` | MongoDB connection string (set to `mongodb://mongo:27017` by Docker Compose) |
| `MONGO_DB`     | No       | `order_agent`               | Database name               |

Never commit your API key to the repo.

## Known limitations

- Conversation history stores only user and assistant text, not tool calls or
  tool results, so follow-ups rely on the agent's earlier reply for context.
- `test_agent.py` is a manual end-to-end script, not an automated test suite
  with assertions.
- The Groq call has a 30-second timeout but no retries, and `/chat` has no
  authentication.

## Design notes / what I'd build next

- Intentionally small (two tools) — the point was proving I understand the
  tool-calling contract end to end, not building a large demo.
- No framework (no LangChain/LlamaIndex): the loop in `agent.py` makes the
  request/response contract explicit rather than hiding it behind an
  abstraction.
- Natural next steps:
  - An eval harness: test questions with the expected tool calls and
    arguments, run on every model or prompt change, with a reported pass rate.
  - A third tool that calls a real external API (e.g. a shipping-carrier
    tracking API) to show multi-source tool use.
  - Retries with backoff on the Groq call, streaming responses, and auth on
    the `/chat` endpoint.
